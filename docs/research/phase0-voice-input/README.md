# Phase 0 技術検証: ブラウザでの音声入力(口頭解答)対応検証

対応Issue: #4

## 背景
筆記だけでなく口頭解答の問題にも対応したい。Webブラウザ上での音声入力・音声認識が
実用に足るかを検証する。
関連: [#10 解答インターフェース(紙PDF出力・タブレットペン入力・口頭解答)](https://github.com/nosetech/kodo-pace/issues/10)、
[#3 Webブラウザ上でのペン入力(手書き解答)対応検証](https://github.com/nosetech/kodo-pace/issues/3)(先行するPhase 0検証)

## 検証方法
[`prototype/`](./prototype) に、ビルド不要・依存ライブラリ不要の素の HTML/CSS/JavaScript
(Web Speech API の `SpeechRecognition` インターフェース)による音声入力プロトタイプを実装した。

```sh
cd docs/research/phase0-voice-input/prototype
python3 -m http.server 8935
# ブラウザで http://localhost:8935/index.html を開く
```

プロトタイプは以下の3セクションで構成される。

1. **実行環境チェック**: セキュアコンテキストか、`SpeechRecognition` APIが利用可能かを自動判定して表示
2. **音声認識テスト**: 「録音開始」ボタンでマイク入力を開始し、確定結果(`isFinal`)・
   未確定の中間結果(`interimResults`)・各確定結果の信頼度(`confidence`)を表示
3. **採点方式検証デモ(簡易版)**: 短答式設問を想定し、認識結果を正規化した上で
   模範解答とのレーベンシュタイン距離ベースの一致度を計算する簡易採点デモ

### 実機での動作確認方法(注意点)

Web Speech API のマイクアクセスは、Service Worker 等と同様に**セキュアコンテキスト
(`https://` または `localhost`)でのみ許可される**仕様である。手書き入力検証(#3)で用いた
`serve.sh`(`http://<LAN IP>:port` でLAN内の実機からアクセスする方式)は、この用途では
**マイクアクセスがブロックされ動作しない**([`prototype/serve.sh`](./prototype/serve.sh)に
同様のスクリプトを用意したが、起動時にこの制約を明示するメッセージを表示するのみに留めている)。

タブレット等の実機で検証する場合は、以下のいずれかの対応が必要になる。

- 実機のブラウザで直接 `file://` ではなく、実機上でローカルサーバーを起動して `localhost` 経由で開く
- 自己署名証明書等でHTTPS配信する
- Chromeの `chrome://flags/#unsafely-treat-insecure-origin-as-secure` に検証用LAN URLを
  登録し、検証目的に限定して「セキュアとみなす」設定を行う(本番運用では不可、あくまで検証用)

本検証は AI エージェント(ローカルPC + Chrome)による実施であり、上記の理由に加えて
**実際に発話できる小学生が手元にいない**ため、**小学生の実発話による認識精度の実測は
行っていない**。プロトタイプ自体の動作(UIの表示、環境チェック、`SpeechRecognition` の
起動・停止がエラーなく行えること)はChrome(デスクトップ)で確認済みだが、
音声認識結果そのものは公開されている research・ドキュメントの調査に基づく評価に留まる。
実測は[今後の課題](#今後の課題phase-1以降への申し送り)に記載する。

## 検証結果

### 1. Web Speech API の対応ブラウザ・仕組み

`SpeechRecognition`(Chrome/Edge/Safariでは接頭辞なし、または `webkitSpeechRecognition`)の
対応状況は以下の通り。

| ブラウザ | 対応状況 |
|---|---|
| Chrome / Edge | 対応。Chrome 139以降はオンデバイス(オフライン)認識にも対応 |
| Safari (macOS 14.1+ / iOS,iPadOS 14.5+) | `webkitSpeechRecognition` で対応。権限付与・言語パック導入後はオンデバイス認識も可能 |
| Firefox | `about:config` の `dom.webspeech.recognition.enable` フラグが必要(既定で無効) |

デフォルトではサーバーベースの音声認識エンジン(Chromeの場合Googleのクラウドサービス)に
音声データが送信され、テキスト化された結果が返る方式である。これは以下2点で重要な意味を持つ。

- **オンライン接続が前提**となる(自宅Wi-Fi内で完結させたい構成(#7)と組み合わせる場合、
  音声認識部分だけは外部サービスへの通信が発生する点に注意が必要。オンデバイス認識に
  対応したブラウザ・OSであればこの制約を回避できる可能性がある)
- **プライバシー**: 児童の音声データが外部のクラウドサービスに送信される。Google Cloud
  Speech-to-Textはストリーミング/同期エンドポイントに送られた音声をメモリ上で処理し
  保存しないとしているが、保護者の同意・プライバシーポリシーへの明記が必要になる可能性がある
  (COPPA関連のFTCガイダンスでは、検索や指示の代替として音声を短時間しか保持しない用途は
  同意取得の適用除外とされているが、教育サービスとしての取り扱いは別途整理が必要)

**受け入れ条件との対応: ブラウザ対応状況を確認した。**

### 2. 小学生の発話に対する認識精度

公開されている研究・ドキュメントの調査によると、以下の傾向が確認できる。

- 一般に、ASR(自動音声認識)エンジンは成人の標準的な発話に対しては高い精度を示す一方、
  **子供の発話では精度が大きく低下する**傾向が広く報告されている。子供は声道の発達過程に
  あるため音響的特徴(基本周波数の高さ・発音の不安定さ)が成人と異なり、汎用ASRでは
  児童特化のモデルに比べて精度が大きく劣るとする研究がある
- 日本語学習者(非母語話者)の発話に対するGoogle Web Speech APIの認識率を調べた2017年の
  研究では、母語話者89.4%に対し非母語話者65.7%という結果が報告されている。子供の発話
  そのものを対象にした日本語ネイティブ音声のデータは今回の調査では見つからなかったが、
  「非定型的な話者(子供・非母語話者・構音障害等)ほど精度が下がる」という傾向は
  複数の研究で一致している
- 小学生、特に低学年は滑舌が未発達であったり、語彙選択が学年相応の言い回しに偏る
  (大人が使わない言い回し・単語の途中での言い淀みが多い)ため、汎用ASRの前提とする
  発話パターンから外れやすいと考えられる

**受け入れ条件との対応: 満たせていない。** プロトタイプは用意したが、実際の小学生の発話に
よる認識精度の実測は、実施環境上の制約(検証者がAIエージェントであり、実際に発話できる
児童が手元にいないこと)により行えなかった。上記の技術的傾向から、**学年が低いほど
認識精度が下がる可能性が高い**という前提でPhase 1以降の設計を進めることを推奨する。

### 3. 採点方式(内容の正誤判定)の検討

音声認識結果をそのまま文字列として使う場合、以下の誤差要因を考慮する必要がある。

- 認識エンジン自体の誤り(特に子供の発話では上記の通り誤りが増える)
- 表記ゆれ(全角/半角、ひらがな/カタカナ、句読点の有無、数字の読み方の揺れ「よんじゅうに」→
  「42」か「四十二」か等)
- 言い淀み・言い直し(「えっと、42、ううん、43です」のような発話)

これらを踏まえ、設問の性質によって採点方式を使い分ける方針を提案する。

**(a) 短答式(一意な正解がある設問。計算問題の答え等)**

[`prototype/app.js`](./prototype/app.js) の採点デモで実装した方式を想定する。

1. 認識結果・模範解答の双方を正規化(全角/半角統一、カタカナ→ひらがな変換、
   空白・句読点除去)する
2. 完全一致すれば正解
3. 完全一致しない場合、レーベンシュタイン距離ベースの近似一致度を計算し、一定の閾値
   (デモでは0.8)以上なら正解、閾値未満だが一定水準(デモでは0.5)以上なら「要確認」として
   人間(保護者・本人)の確認を促す、それ未満は不正解とする
4. 数字の読み上げ(「よんじゅうに」)と数字表記(「42」)の揺れは、正規化だけでは吸収
   しきれないため、日本語の数詞→算用数字変換処理を別途組み込む必要がある
   (Phase 1での実装事項とする)

**(b) 記述式・自由回答形式(説明・理由を答えさせる問題等)**

文字列の完全一致・近似一致では判定できないため、既にPhase 0で検証済みの
[問題自動生成(#16)](../phase0-problem-generation/README.md)と同じ枠組みで、
認識結果のテキストをAI(Claude)に渡し、模範解答・採点基準との**意味的な一致度**を
判定させる方式を採用する。音声認識由来の誤字・言い淀みが含まれる前提で、
「多少の誤字・言い淀みを許容しつつ意味内容が合っているかを判定する」プロンプト設計が
必要になる。

**(c) 信頼度(confidence)の活用**

`SpeechRecognitionResult` は結果ごとに `confidence` を返す(ブラウザ・条件によっては
常に `undefined` を返す実装もあり、プロトタイプではその場合 `(N/A)` と表示するようにした)。
取得できる場合は、信頼度が低い結果に対して「もう一度話してください」と再入力を促す
UIを設けることで、誤認識のまま採点に進むリスクを減らせる。

**受け入れ条件との対応: 満たした。** 短答式はテキスト正規化+近似一致、記述式は
AIによる意味的判定という方針を決定した。ただし数詞変換等の細部は今後の実装課題として残る。
