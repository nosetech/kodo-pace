# Phase 0 技術検証: Webブラウザ上でのペン入力(手書き解答)対応検証

対応Issue: #3

## 背景
高学年向けに紙を使わずタブレット上でペン入力による解答を可能にしたい。
Webブラウザ上(PWA)で実現できるか、ネイティブアプリ(Android/iOS)が必要かを判断する。
関連: [#10 解答インターフェース(紙PDF出力・タブレットペン入力・口頭解答)](https://github.com/nosetech/kodo-pace/issues/10)、
[#11 解答画像アップロードによる自動採点・弱点分析・新規問題生成](https://github.com/nosetech/kodo-pace/issues/11)

## 検証方法
[`prototype/`](./prototype) に、ビルド不要・依存ライブラリ不要の素の HTML/CSS/JavaScript
(Canvas 2D API + Pointer Events API)による手書き入力プロトタイプを実装した。
`prototype/index.html` をローカル HTTP サーバー経由で開くだけで動作する
(Service Worker はセキュリティ上 `file://` では動作しないため、http(s) 配信が必要)。

```sh
cd docs/research/phase0-handwriting-input/prototype
python3 -m http.server 8934
# ブラウザで http://localhost:8934/index.html を開く
```

### 同一Wi-Fi内のタブレットからアクセスする方法

実機での書き味検証のため、[`prototype/serve.sh`](./prototype/serve.sh) を用意した。
サーバーを起動しているPCと同じWi-Fiに接続したタブレットのブラウザから、
プロトタイプに直接アクセスできる。

```sh
cd docs/research/phase0-handwriting-input/prototype
./serve.sh        # ポート省略時は 8934
# もしくはポートを指定する場合: ./serve.sh 8080
```

起動すると、このPC上でのアクセス用URL(`http://localhost:<port>/index.html`)と、
同一Wi-Fi内の端末からのアクセス用URL(`http://<このPCのLAN IP>:<port>/index.html`)が
表示される。後者のURLをタブレットのブラウザ(Chrome等)に入力してアクセスする。
停止する際は `Ctrl+C`。

**前提条件・注意点:**

- サーバーを起動しているPCとタブレットが**同一のWi-Fiネットワーク**に接続されていること。
  自宅Wi-Fiであれば通常問題ないが、ゲスト用Wi-Fiや公共Wi-Fiなど、
  同一ネットワーク内の端末同士の通信を遮断する「クライアント分離(AP分離)」が
  有効なネットワークでは接続できない
- 初回起動時、macOSのファイアウォールが「Pythonが着信接続を受け付けようとしています」
  といった趣旨の確認ダイアログを表示することがある。その場合は許可(Allow)を選択する。
  ダイアログが出ない/誤って拒否した場合は、システム設定 → ネットワーク → ファイアウォール
  から Python の着信接続を許可する必要がある
- タブレット側で表示された `http://<LAN IP>:<port>/` にアクセスしても繋がらない場合は、
  PCとタブレットが本当に同じWi-Fi(同じSSID・同じネットワーク帯)にいるか、
  PC側でVPNが有効になっていないか(VPN使用中はLAN内アクセスが妨げられることがある)を確認する
- **Service Worker(PWA機能)は「セキュアコンテキスト」でのみ動作する仕様のため、
  この方法(`http://<LAN IP>:...`、TLSなし)でアクセスした場合、`app.js` 内の
  Service Worker登録は失敗する**(`app.js` はこれを `catch` して
  コンソール警告を出すのみで、描画機能自体には影響しない)。
  そのため、この手順では[3章のPWA(オフライン起動・ホーム画面インストール)](#3-pwa化での対応可否)
  の検証はできない — 手書き入力(筆圧・追従性・パームリジェクション等)の検証が主目的である。
  PWA部分も含めて実機検証したい場合は、`localhost` 経由(タブレット単体でファイルを配信するか、
  自己署名証明書でHTTPS化する等)の別途対応が必要になるため、まずは本手順で
  手書き入力そのものの書き味を優先して確認することを推奨する

検証した項目は以下の4点。

1. Canvas API / Pointer Events による手書き入力プロトタイプの実装可否
2. タブレット(iPad/Android tablet)のスタイラス入力の追従性・書き味
3. PWA化での対応可否(オフライン動作・ホーム画面インストール)
4. ネイティブアプリとの比較

なお、本検証は AI エージェント(ローカルPC + Chrome)による実施であり、
**実機の iPad(Apple Pencil)/ Android タブレット(S Pen 等)を用いた検証は行っていない**。
2 の「書き味」については、Pointer Events API の仕様・各ブラウザベンダーの公開情報に基づく
技術的な妥当性の確認と、Chrome(デスクトップ)上でのマウス操作によるポインタイベント
(座標・筆圧・coalesced events)の実測に留まる。実機での体感確認は
[今後の課題](#今後の課題phase-1以降への申し送り)に記載する。

## 検証結果

### 1. ブラウザ上での手書き入力プロトタイプ

[`prototype/`](./prototype) に以下を実装した。

- `index.html` / `style.css`: ツールバー(元に戻す・クリア・太さ調整・筆圧トグル・
  パームリジェクション切り替え・PNG保存)とキャンバス
- `app.js`: `pointerdown` / `pointermove` / `pointerup` / `pointercancel` を使った
  描画ロジック
- `manifest.json` / `sw.js` / `icon.svg`: PWA化のための最小構成

Chrome(デスクトップ、マウス操作)で実際に描画・元に戻す・クリア・PNG保存の一連の動作を確認済み。
ペン入力に必須の要素として、以下を実装している。

- **筆圧対応**: `PointerEvent.pressure` を線の太さに反映(筆圧非対応デバイス/マウスでは
  仕様上 `0.5` が返るため、太さトグルで筆圧なしの一定幅描画にも切り替え可能)
- **高サンプリングレート対応**: `getCoalescedEvents()` で、画面の描画フレームレート(60fps)より
  高頻度でブラウザに届く中間点(Apple Pencil は最大240Hz)をすべて拾い、線の欠けを防ぐ。
  検証環境(Chrome)では `getCoalescedEvents` に対応していることを確認した
- **パームリジェクション**: `pointerType === 'pen'` のポインタがアクティブな間、および
  ペン操作直後 500ms は `pointerType === 'touch'` のポインタ入力を無視する簡易ロジックを実装。
  トグルで無効化も可能(タッチのみの端末での検証用)
- **`touch-action: none`**: キャンバス上でのスクロール・ズームジェスチャーへの変換を止め、
  Pointer Events 側にジェスチャーを渡す
- **解像度対応**: `devicePixelRatio` を考慮した Canvas 実ピクセル描画で、Retina/高DPI
  ディスプレイでの滲みを防止

**受け入れ条件との対応: 満たした。**

### 2. スタイラス入力の追従性・書き味

実機での体感検証はできていないため、以下は仕様・公開情報に基づく技術的な評価である。

| 観点 | iPad(Safari) | Android タブレット(Chrome) |
|---|---|---|
| Pointer Events / 筆圧・傾き(tilt)対応 | 対応(iOS 13+ の Safari で `pointerdown` 等が発火し、Apple Pencil の `pressure`/`tiltX`/`tiltY`/`azimuthAngle` を取得可能) | 対応(Chrome for Android は S Pen 等の Pointer Events をサポート。ただしメーカー・OSバージョンによりドライバ実装の差がある) |
| `getCoalescedEvents` によるサンプリング補完 | 対応 | 対応(Chrome 系ブラウザ共通) |
| 入力遅延 | WebKit はネイティブの描画パイプラインに最適化された低遅延パスを持ち、PencilKit 等ネイティブ実装ほどではないが Web でも比較的低遅延との報告が多い | 一般に iOS/Safari より遅延がやや大きい傾向が報告されているが、ミドル〜ハイエンド端末では実用に足るとの報告が多い |
| 既知の制約 | Safari のバージョン・iPadOS のバージョンにより挙動差あり | 端末・OEM(Samsung S Pen 等)ごとの Pointer Events 実装差が大きい |

技術的には Pointer Events API がペンの筆圧・座標・高頻度サンプリングを標準化された形で
提供しており、プロトタイプもそれを正しく利用できていることを Chrome での実測(座標・pressure・
coalesced events の値がデバッグ表示に正しく出ること)で確認した。ただし、**「書き味」として
ユーザーが感じる主観的な追従性(視覚的な遅延の有無)は、実機での確認が本来必須**であり、
本検証だけでは結論を確定できない。実機確認の手順は[今後の課題](#今後の課題phase-1以降への申し送り)に記載した。

**受け入れ条件との対応: プロトタイプでの技術的な実現可能性は確認できたが、
実機(iPad/Androidタブレット)での書き味の確認は未実施。**

### 3. PWA化での対応可否

`manifest.json`(アイコン・`display: standalone`・テーマカラー)と、Cache-first 戦略の
Service Worker(`sw.js`)を実装し、Chrome で以下を実測した。

- Service Worker が正常に登録・`activated` になること
  (`navigator.serviceWorker.getRegistration()` で確認)
- `index.html` / `app.js` / `style.css` / `manifest.json` / `icon.svg` が
  Cache Storage に格納されること(`caches.keys()` / `cache.keys()` で確認)

これにより、初回アクセス後はオフラインでも手書き入力機能自体は起動できる見込みが立った
(解答データのサーバー同期は別途オンライン時に行う設計が必要)。
`manifest.json` の `display: standalone` 設定により、iPadOS Safari・Android Chrome
双方でホーム画面へのインストール(ネイティブアプリ風の起動)にも対応できる想定である
(実機でのインストール動作自体は未確認)。

**受け入れ条件との対応: 満たした。** PWAとして構成可能であることをプロトタイプで確認した。

### 4. ネイティブアプリとの比較

| 観点 | Web(PWA) | ネイティブアプリ(iOS/Android) |
|---|---|---|
| ペン入力API | Pointer Events で筆圧・傾き・高頻度サンプリングを取得可能 | PencilKit(iOS)/ MotionEvent(Android)でより低レベル・高精度な制御が可能 |
| 配布・更新 | URLアクセスのみ、審査不要、即時更新 | ストア審査・インストールが必要、更新に時間がかかる |
| オフライン対応 | Service Worker で対応可能(検証済み) | OS標準機能でネイティブに対応 |
| 開発・保守コスト | 単一コードベース(Web)で iOS/Android 両対応 | プラットフォームごとに別実装、またはクロスプラットフォームFW導入が必要 |
| 手書き認識(文字起こし)の追加実装 | 別途ライブラリ/APIが必要 | iOS は PencilKit + `PKInkAnalyzer`(手書き文字認識)を標準搭載 |
| ローカルWi-Fi運用との親和性(#7) | 高い(自宅サーバーにブラウザでアクセスするだけ) | ネイティブアプリの配布・自宅サーバーとの通信経路を別途設計する必要 |

**結論: Phase 0時点ではネイティブアプリは不要と判断する。**

理由:
- KodoPace の要件(#11)は「手書きの解答用紙を画像として採点AIに渡す」ことが中心であり、
  OS標準の手書き文字認識(PencilKit の `PKInkAnalyzer` 等)を厳密に必要としない。
  採点はアップロードした画像を AI(Claude 等)に渡して行う設計のため、
  文字起こし精度よりも「線が自然に描ける」ことの方が重要
- Pointer Events API で筆圧・高頻度サンプリング・パームリジェクションの基本要素は
  Web だけで実装できることをプロトタイプで確認できた
- #7(自宅Wi-Fi内でのローカル稼働構成)と PWA の相性が良く、ストア配布を伴うネイティブアプリより
  導入・運用コストが低い
- 一方で、実機での書き味(体感遅延)次第では、特定端末(廉価Androidタブレット等)で
  ネイティブアプリ相当の追従性が得られない可能性が残る。この点は実機検証で早期に
  裏付けを取ることを推奨する(「Web前提で進めるが、実機検証で致命的な遅延が確認された場合は
  再検討する」という条件付きの結論)

**受け入れ条件との対応: 満たした。** (結論は上記の通り「ネイティブアプリは不要」だが、
実機検証による裏付けを推奨条件として付与)
